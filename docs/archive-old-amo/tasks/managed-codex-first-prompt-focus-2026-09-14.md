## 本轮讨论结论（2026-09-15）

当前 managed CLI 拉起、Hook 驱动的初步生命周期与 Obsidian 文档审核辅助已有基础。本轮着重连接启动、会话跟踪与 Focus 的实际使用，减少启动后补登记、找会话、安排关注等额外步骤。

推进顺序：

1. **入口**：从明确的本地工程副本发起任务，启动前完成模型、首问与必要的 Focus 安排。
2. **Session 生命周期稳定性**：明确启动、接入、运行、回复、离线及恢复的事实与关联；处理失败、重试、迟到/重复事件，避免错绑、重复执行和遗失工作对象。
3. **Focus 使用效率**：依靠可靠的启动与会话信息，使用户方便找到、处理和安排任务，减少重复维护。人工分组、运行事实与注意力信号仍分开，不能把 CLI 一轮结束直接认定为整个任务完成。
4. **Canvas 后续推进**：待上述流程稳定、能够实际使用后，再提供更直观的工程副本、任务与合并关系呈现。Canvas 本轮不承担全面生命周期控制，不自动扩展相关改造。

现有 priority 在实际使用中没有解决注意力管理问题；本轮不以增加 priority 等级或要求用户再维护一套标签为主要方案。保留既有数据，后续根据入口和 Focus 的使用效果决定取舍。完整 CLI 讨论、人工审核和 Obsidian 文档辅助继续保留；内嵌 CLI/聊天平台不是本轮前提。

## 真实使用场景：同一仓库的多个本地 Unity 工程副本

用户当前因 Unity 工作流不适合采用 worktree 推进需求，在本地保存同一 Git 工程的三份独立副本。通常一份保持闲置，作为应对策划紧急需求的预留副本；另外两份按任务需要切换不同分支、推进不同需求，完成后分别合并。

因此，“多工程管理”在当前场景主要指**同一仓库下多个本地工作副本的任务与占用管理**，不能把它们误当成互不相关的三个产品工程。实施时需要区分：

- 逻辑 Git 工程/仓库：三份副本的共同来源。
- 本地工程副本：具体执行地点，有各自目录和使用情况。
- 当前分支与启动时分支上下文：分支会随工作改变，不适合作为副本的永久身份。
- Task/Card/Session：任务在哪份副本启动、由哪个真实会话执行，以及后续待处理内容。

第一版至少要让用户选清楚具体副本，持续准确关联任务、Session 和执行目录；同一仓库或相似标题不能造成串线。分支变化不能被静默解释为原任务已迁移或已完成。

应急预留是用户的工作安排，不能仅因没有运行 Session 就自动认定该副本可以占用。当前不要求自动分配副本、自动切分支或自动合并。以上是设计约束，尚未锁定新的存储结构；也不限制 AMO 自身开发使用隔离 worktree。

## 目标

用户打开 AMO 的任务启动面板，选好工程与模型，输入首个问题，点击 Run。AMO 拉起交互式 managed Codex CLI，将首问交给该 CLI，并自动把对应工作卡纳入 Focus。用户无需再查找 Session、手动建立关联或补做加入分组。

后续完整讨论、权限确认和审核继续在原 CLI 中进行。Focus 负责记录、提示和返回对话。

## 当前讨论结论与建议的范围

- 用户明确提出上述一键启动及自动纳入 Focus 的目标。
- 用户关注将 CLI 完全内嵌 AMO 的工程量；已比较外部受管窗口、内嵌真实终端、自建聊天界面三个层次。
- 优先打通外部 managed CLI 的入口、稳定会话生命周期与 Focus 流程。内嵌终端或自建聊天界面不在本轮范围。
- 首个交付切口建议以新 Codex CLI 受管启动为主，同时验证断线、重启和恢复时的身份稳定性；具体恢复/归档操作语义需明确设计，不同时覆盖所有 provider 或完整任务决策自动化。
- 点击 Run 表达用户明确要求开始这一轮；首问可以是讨论型问题，也可以是执行要求。CLI 自己的登录、信任和权限流程仍保留。

## 建议的操作流程

1. 用户选择具体的本地工程副本和模型，填写首问；选择或沿用一个有效的 Focus 初始分组。界面应能区分同一仓库的多个目录及其当前分支。
2. Run 先建立可追踪的工作卡和启动请求，再发起一次受管启动。此时显示启动进度，不能虚构已存在的 Session 或宣称首问已执行。
3. 初始问题通过 Codex 支持的启动输入传递。正文作为数据处理，不拼成可执行 shell 片段；验证中文、多行、引号及 PowerShell 特殊字符。
4. 真实 Session 上报后，通过该次 launchId 精确绑定到原工作卡，并接入 Session / Conversation 组件。
5. Card 继续留在用户选择的 Focus 分组。新待审核回复沿用已有 Review 接收规则；没有配置接收组时不自动创建默认组。
6. 用户从卡片返回原 CLI，继续讨论。打开对话不确认处理，也不判断整件任务已经完成。

## 数据与失败处理要求

- Card 保持工作对象身份；launch 记录负责启动事实；Session 身份来自真实运行上报。不要新增一套重复的 Task 持久数据来源。
- 启动前 Card 与 launch 的关联采用什么字段或组件，实施前明确接口；目前不预先规定新组件名称。
- 首次 Session claim 必须绑定原 Card，并协调默认来源索引，避免再自动生成第二张卡。考虑 Session Hook 早于启动接口返回的情况。
- Run 必须有稳定请求身份。双击、失响应重试不能重复拉起 CLI 或重复提交首问。
- 终端启动、Session 接入、首问开始处理是不同阶段；有对应证据后才显示成功。
- 启动失败保留首问和 Card；等待 Hook 超时显示“接入未确认”，不假定终端不存在，不自动重发首问。
- 首问只在本次新启动中提交一次，后续状态观察和 Focus 重开不再发送它。
- 未完成项目接入时，先引导完成明确的工作区接入，不悄悄安装全局 Hook或绕过信任确认。

## 实施时仍需明确的边界

1. 没有可用 Focus 分组，或已记住的分组被删除时，如何引导选择/创建；不能自动造固定分类。
2. 新入口的打开位置、工程副本和应急预留标记如何复用/补足现有工作区数据。
3. 启动请求幂等、未知执行结果的恢复与首问交付证据；界面中的简单重试必须有可靠运行层支撑。
4. 启动前 Card 与 launch 的原子关联及 Session claim 顺序，避免真实 Hook 提前到达造成重复 Card。
5. 按独立的小轮次交付：先落实入口，逐步接入可靠启动与 Focus，不以这次原型确认作为全面生命周期或 Canvas 改造授权。

## 建议验收

- 同一 Git 仓库的三份本地副本可以准确区分。任务在选定副本启动，不误用应急预留副本；相同仓库、分支名或相似标题不造成 Session 串线。
- 在已接入工作区选择模型、输入首问，点击一次 Run，只启动一个 managed CLI。
- 所选模型配置准确传入；中文、多行和特殊字符首问完整传递，不执行其中的 shell 字符。
- 从点击 Run 起就能在 Focus 找到同一张 Card；真正 Session 接入后身份不变、不重复生成卡。
- 终端启动失败、未收到 Hook、登录/信任等待和接口失响应都有准确反馈，首问不丢失、不自动重复发送。
- 重复点击或重试不会制造第二个终端；新回复可沿用 Review 接收规则，卡片可返回正确 CLI。
- AMO/Broker 重启后能够重新核对启动与绑定事实，不凭旧状态自动重新执行首问。
- 先使用隔离数据、模拟启动器和临时工作区验证；真实首问执行需使用明确授权的测试内容，不能拿生产任务做自动启动试验。
