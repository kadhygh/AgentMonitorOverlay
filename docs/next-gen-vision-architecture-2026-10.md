# AMO 下一代：愿景与架构草案

日期：2026-10-12。状态：方向已确认（第 9 节），下一步拆分阶段 1。

依据：

- 用户在 2026-10-12 讨论中确认的方向
- [协议驱动 Session 技术验证](protocol-session-spike-2026-10-12.md)

## 1. 为什么重新设计

当前 AMO 是多次缩减范围后形成的方案：悬浮窗、Obsidian 插件，加上 hook 监控外部 CLI。它解决了最初的三个痛点：

- 认真阅读长回复；
- 多个工程、多个 CLI 并行时，能看清各自状态；
- 跨天以后，能接上原来的任务。

但它已经撑不起下一步的目标，原因有两个：

- **hook 只能看到"又出现了一个 session"。** side chat、resume、new、subagent 之间是什么关系，hook 无从得知，单线的管理方式无法表达这种结构。
- **悬浮窗太小。** 放不下看板和画布这类组织层的界面。

与此同时，模型能力已经足以支撑一次完整的重新设计。技术验证也证明了，协议驱动的 session 可以和原版 CLI 互通。这次允许颠覆现有底层架构，也不再限定使用 Tauri。

## 2. 愿景

> **AMO：由人主导、agent 也能参与的项目推进工作台。**

- **核心交互不变。** 仍然是人拉起一个 session，通过对话指导它完成单个任务。对话可以在工作台的对话面板里进行（参考 DSH 的对话方式），也可以随时接入原版 TUI。两者连的是同一个 session。
- **审阅进入工作台。** 回复以 markdown 渲染，支持快速跳转和定位批注，批注可以整理后发回 session。不再依赖 Obsidian。
- **AMO 负责组织层和上下文层。** 需求、看板、画布、session 之间的关系、项目上下文，都由 AMO 管理。
- **所有层级都有接口。** 人通过界面操作，agent 通过 MCP 操作，双方使用同一套接口。session 之间也通过 AMO 互相传话。
- **面向项目扩展。** 可以针对具体项目接入专门的规范、流程和工具。
- **不限定项目类型。** Unity 是第一个使用场景，也可以用于其他项目。
- **只发布 Portable 版本。** 首次启动时，如果没有关联数据目录，就进入设置流程。

## 3. 明确不做

- 不做 vibe-kanban 那样的重度流程。不强制使用 worktree，Unity 工程尽量不用。
- 对话面板不追求与原版 CLI 功能对齐。斜杠命令、`/model` 等暂未实现的能力，通过接入原版 TUI 使用；对话面板按实际使用情况逐步补齐。
- 不做自动审批。未经人确认，不让 agent 自动执行高风险操作。
- 不绑定单一厂商的运行时。DeepSeek Harness 只作为参考，以及可选的第三种运行时。

## 4. 核心对象

| 对象 | 职责 | 说明 |
|---|---|---|
| Workspace | 一个真实的工程目录 | 沿用现有工作区登记 |
| Area | 业务范围，可以跨多个 Workspace | 例如 Project Mining 包含三个 Unity 工程。保存说明、上下文和常用链接 |
| 任务 | 一项要推进的工作，属于一个工作区 | 有自己的状态（看板列，由人调整），包含多个独立会话；每个会话有自己的模型，并带着各自的分支和子 agent。任务状态和会话运行状态分开记录 |
| Session 树 | 一次对话及其分支 | 主 thread，加上 fork、side chat、subagent。父子关系由 AMO 在创建或观察到相关事件时自己记录，因为两家的列表接口都不提供 |
| 项目上下文 | 规范、注释、Scratchpad、回复与批注 | 人可以在工作台查看，agent 可以通过 MCP 读取 |
| 批注 | 锚定在某条回复的具体位置 | 在工作台中添加，可以汇总后作为一轮输入发回 session |
| 项目扩展包 | 针对某个项目的专门功能 | 见第 7 节 |

看板显示任务，画布显示需求与 session 树之间的关系。悬浮窗只做 Focus：查看进度和最新内容。

## 5. 架构

```text
          ┌──────────── 客户端（Electron）────────────┐
          │ 工作台：看板/画布/对话/审阅   Focus 悬浮窗 │   原版 Codex TUI (--remote)
          └──────────────┬────────────────────────────┘   │
                         │ HTTP / WS（UI API）              │
     agent ── MCP ──►┌───┴─────────────────────────────┐   │
                     │      AMO Host（Node，常驻）       │   │
                     │  Store：卡片 / session 树 / 事件   │   │
                     │  Router：模型路由与凭据            │   │
                     │  Runtime 适配                      │   │
                     │   ├ Codex：自持 app-server (WS) ◄─┼───┘
                     │   ├ Claude：Agent SDK             │
                     │   ├ Hook 观察：野生 CLI 兜底       │
                     │   └ DSH sdk/acp（以后）            │
                     └───────────────────────────────────┘
```

### 5.1 Host

- 常驻的 Node 进程，生命周期独立于任何界面窗口。验证中，TUI 断线后会自动重连，所以 Host 不能随界面一起开关。
- 新写，不在现有 broker 上改。工作区登记、凭据读取、模型 profile 等确实需要的逻辑按需搬入新代码，不保留旧接口和旧数据兼容。
- 对界面提供 HTTP/WS API；对 agent 提供 MCP。

### 5.2 Session 托管模式

| 模式 | 适用场景 | 行为 |
|---|---|---|
| 共享托管 | Codex | Host 自己持有 WebSocket app-server。原版 TUI 通过 `codex --remote` 接入，AMO 和 TUI 是同一个 server 的客户端，双方实时看到对方，没有写入冲突 |
| 交接托管 | Claude | 用 Agent SDK 驱动。需要用原版 CLI 时，执行 `claude --resume <id>` 交接；交接期间 AMO 侧只读，CLI 退出后再收回 |
| 观察 | 用户在外部随手开的 CLI | 继续用 hook 观察状态，可以手动收编进 AMO |

**单写者规则：** 不经过同一个 server 的并发写入，两家都会静默丢失内容。所以同一个 session，同一时刻只允许一方写入。Host 记录当前持有写入权的一方，界面上要显示出来。

### 5.3 模型路由

- 沿用现有 profile 和 Credential Manager 中的 Key。
  - Codex：通过 app-server 启动参数或 thread 参数注入 provider。
  - Claude：通过 SDK 的 `env` 注入。
- DeepSeek 和 GLM 作为弱模型，与 Codex、Claude 默认模型同等可选。验证中两者都已经跑通。
- Key 只放在进程环境里，不进命令行、不进日志、不进 Store。

### 5.4 技术栈

与 DeepSeek Harness 桌面版同技术：Electron + React + Vite + TypeScript。DSH 的界面按功能拆成模块（`ui-conversation`、`ui-tool`、`ui-subagent`、`ui-permission-presets` 等），为 MIT 许可，作为对话面板和工具调用展示的主要参考。复用代码时，在 `THIRD_PARTY_NOTICES.md` 中注明出处。

选择理由：后续会持续增加便利性的界面功能，Electron 做复杂界面的能力在三种外壳中最强，前端生态也最完整。

需要单独处理的原生能力：

- **Focus 悬浮窗的透明与点击穿透**：Electron 支持透明无边框窗口，以及 `setIgnoreMouseEvents(true, { forward: true })`。需要在 Windows 上实测，包括多显示器和 DPI。
- **跳转外部窗口**：调用 Win32 的窗口激活接口。可以把现有 Rust 实现编译成一个小工具复用，也可以通过 Node FFI 调用。

代价：内存占用和 Portable 包体积（100MB 以上）都大于 Tauri。

### 5.5 对话面板

数据来源：

- **Codex**：app-server 的结构化事件，包括回复增量、推理摘要、命令执行、文件改动与 diff、计划更新、审批请求。
- **Claude**：Agent SDK 的消息流。

最小可用版本包含：

- markdown 回复与流式显示；
- 折叠的工具调用卡片；
- 审批（批准/拒绝）；
- 中途插话（`turn/steer`）与打断（`turn/interrupt`）；
- 子 agent 嵌套显示。

对话面板与审阅共用同一套 markdown 渲染：在回复上直接定位批注，汇总后发回。功能缺口通过接入原版 TUI 补位，不在第一版追求齐全。

## 6. 面向 agent 的 MCP 接口

Host 在启动受管 session 时注入 AMO MCP，权限分级开放：

| 级别 | 能力 | 开放时机 |
|---|---|---|
| 只读 | 读取看板、任务、session 树摘要、项目上下文、扩展包规范 | 阶段 4 |
| 写自身 | 更新自己所属任务的进度和备注，提交交接摘要 | 阶段 5 |
| 信箱 | 给其他 session 或任务留言。接收方在下一轮读取，或者在回合结束时收到提示；由人决定何时处理 | 阶段 5 |
| 请求决策 | 向人提出需要决策的问题，显示在 Focus 和工作台中 | 阶段 5 |
| 派发 | 新建 session，或者向其他 session 投递任务 | 暂不开放，需要单独评审 |

## 7. 项目扩展包

放在工程内的 `.amo/packs/<name>/`，由一份 manifest 声明以下内容：

- **规范引用**：规范文档、配置表说明、常见坑。工作台里可以直接查看，agent 通过 MCP 也能读到。
- **流程模板**：新建某类需求时，自动带上步骤和检查清单。
- **启动预设**：从卡片一键拉起 session，自动带上提示词模板和相关上下文文件。
- **专用工具（以后再做）**：针对项目的 MCP 工具，例如查询武器配置表。

先预留扩展接口，不预设具体内容。扩展包的实际形态以各个 project 的具体需求为准，长期迭代。"武器逻辑开发"是已知的候选场景之一。

## 8. 分阶段交付

每个阶段完成后都能单独投入日常使用。

| 阶段 | 内容 | 验收 |
|---|---|---|
| 0 ✅ | 协议验证 | 见验证报告 |
| 1 | **Host + Codex 共享 session + 最小对话面板**：常驻 Host 管理 app-server；在工作台中新建或恢复 thread 并对话；一键用 `--remote` 接入原版终端；事件写入 Store；自动记录 fork 和 subagent 的父子关系 | 日常使用 Codex（包括 DeepSeek）可以在工作台完成；需要时切换到终端，体验与原来一致 |
| 2 | **审阅**：回复 markdown 渲染、快速跳转、定位批注、批注汇总发回 | 不打开 Obsidian 也能完成现有的审阅闭环 |
| 3 | **组织层**：任务、看板、session 树画布、从卡片启动 session；Focus 悬浮窗接入 Host | 一个真实需求可以在工作台上从创建一直推进到完成 |
| 4 | Claude 交接托管、GLM 路由、只读 MCP | Claude 和 GLM 的 session 进入同一棵树；agent 能读取看板和上下文 |
| 5 | 可写 MCP、信箱、请求决策 | 两个 session 能通过 AMO 交接信息，由人掌控节奏 |
| 6 | 项目扩展接口 | 至少有一个真实 project 的扩展包在使用中 |
| 以后 | DSH 作为第三种运行时、AI 主控规划、Portable 首次启动设置 | 另行规划 |

现有 AMO 在新版达到阶段 3 之前继续作为日常工具，不做新功能，只修阻断问题。

## 9. 已确认的决定（2026-10-12）

1. **审阅搬进工作台。** 实际工作大多是给指定位置加批注，所以只做 markdown 渲染、快速跳转和批注，不再依赖 Obsidian。
2. **新旧分开。** 翻新的内容较多，不让旧代码束缚新设计：新版在独立的子工程中开发，旧 AMO 原样保留，作为过渡期的日常工具。
3. **工作台要有输入框。** 采用类似 DSH 的对话方式。
4. **技术栈与 DSH 相同**（Electron + React + Vite）。后续会持续增加便利性的界面功能。
5. **项目扩展先预留接口。** 以具体 project 的需求为准，长期迭代。
6. **任务是外层概念。** 一个任务包含多个独立会话（例如一个实现、一个审阅），会话可以使用不同的模型。
   - **任务可以跨工作区**：会话各自指定所在的工作区。数据模型从第一天起就要支持这一点。
   - **会话可以归档**：归档时，它下面的分支和子 agent 一起归档，收进会话列表底部，可以恢复。
   - **全局待办和调度 agent 放在后续开发**：调度 agent 定期检查空闲的工程，认领待办并开出会话，开工前交给人批准。这一项排在可写 MCP 之后。
   - **画布是无限画布**：可以平移和缩放，分组由人自由创建、移动、调整大小，也可以选择绑定一个工作区，供调度 agent 判断该工程是否空闲。画布内容（分组、任务、依赖、便签）存成结构化数据，供 MCP 的 `canvas.read` 直接返回，agent 不需要读坐标就能理解画布；写入接口以后开放。
7. **交互细节由设计预览确定。** 预览地址为 https://claude.ai/artifact/LyWa7NybnLR3Ro84wdGPgv（模拟数据）：
   - 新任务直接建在当前选中的工作区；
   - 批注通过选中文字后右键添加。

   后续的体验细节记录在 `studio/design/interaction-notes.md` 中，边做边补充。

## 10. 进入实现前还需补测

- 在 TUI 中执行 `/fork` 和 side chat 时，AMO 侧收到的事件；
- AMO 与 TUI 同时在线时，审批请求由哪一方响应；
- Host 重启后，TUI 重连能否回到原来的 thread；
- 一个 app-server 能否让不同 thread 使用不同的 provider，还是需要每个 provider 一个进程；
- Electron 透明悬浮窗在 Windows 上的点击穿透与多 DPI 表现（可以推迟到阶段 3）。
