# 工程框架评估：增删模块是否方便（2026-10-13）

> 用户 2026-10-13 同意按这份建议重构，分支 `studio/stage-11-modules`。做完的结果见文末"实际做法"。

## 现状

| 层 | 内容 | 规模 |
|---|---|---|
| `protocol` | 实体、接口类型、纯函数（会话树、画布布局、范围、调度…） | 约 1300 行；`api.ts` 一个文件列出全部 65 条路由和事件 |
| `host` | `service.ts`（全部业务）、`http/server.ts`（路由表）、`store/`（SQLite + 迁移）、`runtime/`（Codex / Claude）、`mcp/`（工具） | `service.ts` 1350 行、100 多个方法 |
| `ui` | 按页面分目录（board / canvas / task / newtask / chat / packs / settings / focus），`App.tsx` 手写视图切换 | 样式三个大文件：`app.css` 680 行、`chat.css`、`compose.css` |
| `app` | Electron 外壳 | 约 800 行 |

**做得好的地方**

- 运行时已经是插件式的：`RuntimeRouter` 按会话或模型配置分发到 Codex / Claude，再加一种运行时只需要实现 `SessionRuntimeApi`。
- 协议层是纯类型加纯函数，Host 和界面共用，类型检查能把改动波及的地方都找出来。这次加"专题"就是靠它一次改全的。
- 测试分层清楚：纯函数单测、接口测试（假 app-server）、端到端测试（mock 模型），改动有安全网。

**不方便的地方**

1. **一个功能散在很多文件里**。加"专题"改了 12 处：实体、接口类型、迁移、存储、`service.ts`、路由表、MCP 工具、MCP 读模型、界面状态、左栏、页面、样式。删一个功能也要在这些地方逐个找。
2. **`service.ts` 是大杂烩**：任务、专题、会话、留言、决策、清单、待办、调度、扩展包、画布、批注、设置、凭据都在一个类里，越来越难读，也很难单独删掉某一块。
3. **路由表、MCP 工具表、事件类型都是一张大清单**，没有"这个功能自带哪些路由和工具"的边界。
4. **界面没有功能注册**：视图在 `App.tsx` 里手写分支，设置页的分区也是写死的，一些不常用的功能（扩展包、调度、整体待办）没法一键隐藏。
5. **样式按"页面阶段"堆进大文件**，同一个组件的样式可能分在两个文件里。

## 建议：按"功能模块"组织

每个功能一个目录，自己带齐它的全部东西，再在一个清单里登记：

```
host/src/features/topics/
  service.ts      ← 只管专题的业务（从 service.ts 拆出来）
  routes.ts       ← 这个功能的 HTTP 路由
  mcp.ts          ← 这个功能给 agent 的工具
  store.ts        ← 这个功能的表的读写（迁移仍是全局有序的一张表，只是标明属于哪个功能）
ui/src/features/topics/
  TopicPage.tsx、nav.tsx、topics.css
```

- Host 启动时遍历功能清单，汇总路由和 MCP 工具；去掉一个功能 = 删目录 + 删清单里一行（已有的数据表保留，迁移永远不删）。
- 界面也有一份功能清单：视图、左栏条目、设置分区、快捷键都从清单生成。可选功能（扩展包、调度、整体待办、Focus）可以在 设置 → 功能 里开关，关掉就不出现。
- 协议的路由类型按功能拆文件，用类型交叉合成 `HostRoutes`，类型检查照样覆盖全部。
- 共用的东西留在核心：存储连接、事件发布、运行时、身份与权限、设计变量和基础组件。

## 分步做（每步都不改行为，跑完 verify + 端到端再进下一步）

| 步骤 | 内容 | 风险 |
|---|---|---|
| R1 | 把 `service.ts` 按领域拆成几个服务类（任务与专题、会话、协作、画布、待办与调度、扩展包、设置与凭据），共享一个上下文对象 | 低：纯搬家，接口测试全覆盖 |
| R2 | 路由和 MCP 工具改成每个功能自己声明、启动时汇总 | 低 |
| R3 | 界面按功能建目录，视图、左栏、设置分区从注册表生成；样式跟着组件走 | 中：界面改动面大，靠端到端测试兜底 |
| R4 | 可选功能开关（设置 → 功能），先把扩展包、调度、整体待办做成可关 | 低 |

预计 R1、R2 各半天，R3 一天左右，R4 半天。建议在阶段 10 的界面改版收尾后、开始做新功能之前做，因为 R3 和界面改版会动到同一批文件。

## 实际做法（2026-10-13）

**Host**

- `host/src/service.ts` 只剩组合根（约 130 行）：存储、运行时、事件、各功能共用的查找和校验。业务在 `features/<名字>/service.ts`，10 个功能类：projects、config、tasks、topics、sessions、planning、collab、canvas、review、packs。它们都继承 `core/feature.ts`；跨功能调用写成 `this.f.<功能>.<方法>`，一眼能看出哪里依赖了别的功能。
- 每个功能的 HTTP 路由在 `features/<名字>/routes.ts`，MCP 工具在 `features/<名字>/mcp.ts`。功能清单 `features/index.ts` 把它们汇总起来，服务器和 MCP 都从清单读取。
- 存储（`store/`）和迁移没有拆。SQLite 的表之间有外键，迁移要求全局有序，拆开反而更难管。功能的读写仍然通过 `Store`。
- 协议的路由类型（`protocol/src/api.ts`）暂时没拆。它是 Host 和界面之间的契约，放在一个文件里查起来更方便；等它明显变长再拆。

**界面**

- 页面按功能分目录。原来放在别人目录里的面板搬回了自己的功能目录：`planning/`（整体待办、调度提案）、`collab/`（留言、决策、进度、清单）、`review/`（草稿区、批注）。
- 每个功能用 `view.tsx` 声明自己的页面和顶栏标签，`ui/src/features.ts` 是界面这边的功能清单。`App.tsx` 只剩外壳：连接、范围、当前页、顶栏、左栏。顶栏标签由清单生成。
- 样式跟着功能走（`board/board.css`、`canvas/canvas.css`…），`styles/` 只留设计变量、基础控件和 Markdown。整个界面打包成一份样式，所以 `main.tsx` 统一按"基础在前、功能在后"的顺序导入，顺序本身就是层叠顺序。
- 设置分区没有做成注册表：现有分区（界面、公共目录、预设、凭据）都属于核心，R4 新增"功能"一节。

**增删一个功能现在要动哪里**

| 位置 | 内容 |
|---|---|
| `host/src/features/<名字>/` | `service.ts`、`routes.ts`、`mcp.ts` |
| `host/src/features/index.ts`、`host/src/service.ts` | 各加一行 |
| `protocol/src/api.ts` | 路由和事件类型 |
| `store/` | 有新表时加迁移和读写 |
| `ui/src/<名字>/` | 页面、`view.tsx`、样式 |
| `ui/src/features.ts`、`ui/src/main.tsx` | 各加一行 |
