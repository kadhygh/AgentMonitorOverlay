# 交流架构之后：AMO 整体怎么借鉴

状态：待确认（2026-11-25 协调会话「AMO / 中转迭代讨论」写的建议，用户还没看。用户 11-25 要的第二份报告：「此轮迭代完之后，我们后续 amo 怎么借鉴这套推进到整体 amo」）。HTML 版在旁边 `amo-collab-next.html`。

这一轮在协作里打通的东西见 `plans/collab-framework.md`（人这边）和 `plans/collab-agent-spec.md`（AI 这边）。本文只说：哪些做法值得变成 AMO 的通用骨架，按什么顺序推到别处，哪些先不碰。

## 一句话

AMO 以后的每一块（任务、专题、值守、问题页、中转、便签待办）都按同一个骨架长：**事实只记成事件 → 状态和「待我处理」由事件算出来 → 人和 AI 各看自己那一份 → 少数几类事必须停下来等人**。这一轮验证了这个骨架在最难的场景（两个人、多个 AI、跨机器）里站得住，下面是把它推回 AMO 其余部分的办法。

## 这一轮里站得住的六个做法

1. **事实是事件，状态是算出来的。** 事项的「在做 / 等对方 / 等人确认 / 已推送 / 待核对 / 已验 / 关闭」不靠谁去改，按事件（开、@、回、绑、推、验、问人、结论）推。板是事项的画法，只存人拖过的位置。结果：真模型两组跑下来，状态在每个时刻都对得上；验收前（11-24）状态全靠主控记得改，经常落后。
2. **每条消息对每个收件人都有回执，「待我处理」是算出来的一张表。** 排队 → 送到 → 看过 → 处理了；看过是自动的，处理了要显式标（或回复）。人和 AI 读的是同一份数据，只是过滤不同。
3. **角色是一张卡，Host 负责它一直在场。** 主控 / 执行 / 任务主控各一张卡；开局写进 instructions，变了在下一条消息里带全卡，压缩后补全卡，`amo_whoami` 随时给。AI 不用人提醒就知道自己是谁、能用什么工具。
4. **巡检代替常驻 agent。** Host 每 2 分钟替每个主控算一次「待我处理」，只有新东西才叫醒，忙着就等它这一轮结束。没事不花 token（10-30 定的「不常驻看板员」在这里落地了）。
5. **闸门是一张短表，其余 AI 之间自己谈。** 只有判红、改已定口径、合 master、动别人的东西、对外发布要停下等人；AI 之间回答边界时写来源（和人确认过 / 我的判断），「我的判断」自动知会到它代表的人。人看得少了，但该看的一定会看到。
6. **规格先行，用真模型验收，一版版改到数字过。** 规格 v1 → v6，每版三种模型各跑一遍，按 9 项打分（状态对不对、闸门停没停、越权几次、空叫醒几次、每轮 token……）。这套模拟环境（`spikes/collab-spec-eval/`、`spikes/cowork-scenario/run2.mjs`）本身就是资产。

## 推到 AMO 其余部分：建议的顺序

每一步都是「把那一块的事实改成事件 + 让它进同一张待我处理」，小步、可单独发版。

| 步 | 哪一块 | 现在 | 改成 | 为什么排这里 |
|---|---|---|---|---|
| 0 | 协作本身 | 刚发测试版 | 明天起真用，收反馈；只修，不加 | 骨架要先在真人手里过一轮 |
| 1 | 任务看板 | 列（待办 / 在做 / 待审 / 完成）靠人拖、靠 AI 自己说 | 任务的列也由事件推：会话开始 → 在做；交接、提交、验证 → 待审；人确认 → 完成。人拖算「手改」 | 本机的事项和消息（`ce09967a`）已经有了，离得最近；看板是人每天看的地方 |
| 2 | 专题和画布 | 主控手动摆卡、写说明 | 画布像协作的板一样由任务和事项算出来，只存人拖过的位置；专题主控的「待我处理」走同一个巡检 | 去掉「主控要记得改画布」这件事，和协作同一个毛病 |
| 3 | 值守和问题页 | 问题页状态、自动打包失败各有各的通知 | 一个问题 = 一件事项；打包失败、合并、发布是它的事件；值守就是这类事项的执行 | 值守是最常跑的自动流程，最先受益于「状态别靠人改」 |
| 4 | 一张「待我处理」 | 协作、本机两组已经并进来 | 加上问题页、值守、中转聊天、便签待办，一处看完；Focus 只显示条数和最急的一条 | 人只该有一个地方回答「现在要我做什么」 |
| 5 | 任务管家 / 全景（11-13 的方向 2） | 没开始 | 不做常驻 agent：管家 = 人自己的「任务主控」+ 巡检，全景 = 待我处理 + 各板的合并视图 | 前 4 步做完，管家要的数据就都在了，不用另起一套 |

## 每一步都守的几条

- **先定数据和事件，再画界面。** 一块要改，先写出它的事件表和推导规则（像 `protocol/src/matters.ts` 的 `applyMatterEvent`），纯函数、两端共用，界面只是画法。
- **算出来的东西不存。** 状态、在等谁、待我处理、板上的位置（人拖过的除外）都现算；存的只有事件和人手改的。
- **旧的照常能用。** 每改一块就在健康检查里加版本号（像 `cowork: 2`），旧客户端、旧服务器走旧路，有单测守着（这轮 `cowork-old-service.test.ts`、「旧客户端连新服务器」那组）。
- **AI 这边的规格和角色卡一起改、一起验。** 改了卡的措辞，就用模拟环境跑一遍三种模型，数字不能变差；把它当成卡片改动的回归测试。
- **闸门表只增不乱加。** 新的一块要停下等人的事，先问是不是已有五类之一；不是再加，加了要写清「什么算、什么不算」。
- **一次只开一块。** 每步做完发一版测试，真用过再开下一块（守 11-15 的「在测试通道上给能用的切片」）。

## 先不碰的

- 不做常驻的管家 / 看板员 agent（token；10-30 的决定）。
- 不做跨团队、公网的协作：中转仍然只在局域网，自己的设备（远程默认关）。
- 便签不并进事项，只让它的待办出现在待我处理里。
- 不一次把所有消息都改成事项：本机留言已经改了，中转聊天（人和人）保持聊天，只有被 @ 的进待我处理。

## 要留意的风险

- **token**：gpt 当主控时每轮输入中位约 108 万（sonnet 约 9 万）。联调正在拆是 `cowork_read` / 叫醒给多了还是 Codex 自己的上下文；结论出来前，gpt 不当主控。
- **小事被结构压住**：一两轮就能做完的事也要开事项、写结论，可能比原来慢。观察真用时人会不会绕开事项直接聊。
- **模型差异**：每版每种模型只跑了一次，数字有偶然性；规格措辞对某个模型有效不等于对新模型有效，换模型要重跑。
- **「要你看」变多**：推断自动知会、关事项通知都会进人的列表。如果人觉得烦，先合并同一事项的多条，而不是去掉。

## 要用户定的

1. 顺序是否按上表（先看板、再画布、再值守和问题页）？还是先值守（自动打包、问题页每天都在跑）？
2. 任务看板的列改成由事件推之后，人还要不要能手拖？（建议：能拖，算手改，下一个事件照常推。）
3. 模拟环境要不要变成固定的回归：改角色卡、改 MCP 工具描述就跑一遍（每次大约 claude 20、gpt 25、deepseek 20 轮额度）？
