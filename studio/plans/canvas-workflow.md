# 画布工作流 canvasflow（2026-10-30，方向讨论，细节未定）

还在讨论阶段，没有开工。下面是 10-30 和用户聊下来的方向，标「未定」的地方等用户想好再补。

## 要解决的问题

用了一阵 Studio + Focus，管理和协作顺手多了，但工作里有两个痛点还在：

1. **专题用得少。** 手上大多数事 1～3 个会话就能做完，所以一般直接开任务。之前试过「人只做决策」，但如果对需求和进展的细节不熟，推起来还是难受。
2. **一个会话里的事会丢、会缠在一起。** 一轮回来 10 个问题（有要人拍板的决定，也有 bug 和审阅意见），人一次只能回 1～3 个，剩下的往后放；中间人会想到要补充，或者就某一条展开聊好几轮，甚至在某一轮里又分出几条支线（有时同时推进，有时一条一条来）。结果是前面几轮留下的问题经常忘了处理，几次展开之间有关联也对不上。

原因：AI 交回来的是一组待处理的事，但会话是一条直线的聊天。没回的问题没有记号，只能靠人记；支线之间的关联散在聊天记录里，没有地方汇总。上下文压缩时，AI 也会丢这些细节，所以一个主会话撑不住这种规模。

## 方向：白板就是记忆

像科研白板那样推进：问题、线索、结论、便签、图片、图表都放在画布上，陆续展开。人和所有会话都读写同一块板，谁都不用把整件事装在自己脑子里或上下文里。

```
人
 │ 看、摆、拍板、贴便签
画布白板（卡、连线、结论、图、便签）  ← 唯一的事实来源
 │ 协作 MCP：读板目录、交结论卡、自报关联、提问
多个会话（开几个、怎么分工，对人隐藏）
 │
代码：连带复查、变化标记（不用模型）
```

- **人不用关心会话，但要关心白板。** 会话开了几个、怎么分工，是幕后的事；但「只做决策」不顺的教训说明，人还是要看到过程，只是看板上的结论、证据和图，不看聊天记录。
- **专题就是白板**，用在一个任务装不下、问题会分叉的事上。1～3 个会话能做完的事照旧直接开任务，不经过白板。专题用得少不是毛病。
- **小事和大事的分界**：未定（比如任务开到第 N 个会话，或问题卡很多时，提示升级成白板？）。

## 角色

| 角色 | 做什么 | 不做什么 |
|---|---|---|
| 人 | 摆布局、贴便签和图片、拍板、在卡上点「展开」 | 不用记住全部 |
| 分支会话（按需开，可以并行） | 在某张卡上展开时才开。上下文只有：这张卡、它的上游、相关的已定结论、板的目录。干完往板上交结论卡，并写明「影响到 #3、#7」 | 不读别的分支的聊天，只读板；只写自己那一块 |
| 代码 | 结论变了，沿连线把下游卡标「需复查」；按时间标出「上次以来」变过的卡 | — |

**常驻的看板员（主控）先不做**（10-30 用户的意见）：让一个会话常驻维护整块板，它每次都要重读整块板和各条线的需求，板越大越费 token。它原来要做的事拆开分给别人：

| 原来看板员的活 | 现在谁做 |
|---|---|
| 找出牵连 | 交结论的分支会话自报（它手上有上下文，几乎不多花） |
| 连带复查 | 代码沿连线标「需复查」 |
| 上次以来变了什么 | 代码按时间标记；一句话总结以后再说 |
| 重叠的卡合并、整理 | 人手动拖；或人圈几张卡，让 AI 只整理这几张 |
| 全板扫一遍、自动合并 | **延后**，等用一阵、看清漏掉的牵连多不多再定 |

分支会话只看自己那条线，可能不知道板上还有别的相关卡。补法：交卡前读一份板的目录，只有标题和一句话结论，不含正文。`canvas_read` 现在的 outline（`#n【状态】标题` + 结论第一段）已经接近这个样子。还是漏了的，人在板上看到后补一条连线，后面的连带复查就会跟上。

## 规矩（防止板变乱）

1. **布局归人。** AI 不重新排人摆好的卡（人看白板靠位置记忆）。新卡放在源卡旁边，或者放进一个「新到」区，由人拖走。
2. **分支会话只写自己那一块。** 跨卡的连线、合并、拆分，由 AI 提议、人确认，和第 15、16 阶段「主控提议、你确认」同一个思路。
3. **图表挂在卡上。** AI 画的流程图、对比表作为卡的附件，不在板上另开一摊。
4. **没回的问题不会悄悄消失。** 卡一直保持「待看」，直到人回答、搁置或标为不做。
5. **「上次以来」要显眼。** 打开板时，变过的卡有标记。

## 已经有的基础（据 10-30 的代码）

画布审阅（`host/src/features/canvasreview`，方案 `plans/review-canvas.md`）基本就是这件事的雏形：

- `canvas_items_post`：把问题铺成编号卡（#n），状态有 待看 / 已确认 / 要讨论 / 搁置 / 完成；`canvas_item_update` 写结论；
- `canvas_callout`：在卡上挂说明或提问气泡，人的回答以「【画布回答】」回到提问的会话；
- 「就这条展开聊（新会话）」：在发起会话所在的任务里，为一张卡开一个会话，卡上记 `threads`，并显示子对话的状态（`ui/src/canvas/review.tsx`）；
- `canvas_read`：outline 可以直接当板的目录用。

## 做成什么形式

按 Studio 现有的**功能模块**来加，不做运行时安装的插件：

- Host：`host/src/features/canvasflow/`（service、routes、mcp），在 `features/index.ts` 登记；
- 界面：`ui/src/canvasflow/`，在 `ui/src/features.ts` 登记；
- 复用画布、审阅条目、任务和会话，不改它们的内部逻辑；在卡上「展开」，就是在这个专题下开任务和会话，任务、会话、委派、额度都沿用；
- 设置里可以关掉（`settings:disabled-features`）。

## Focus：一个 flow 一行

例子：一个 canvasflow 拉起 4 个会话，其中有卡住的或有事等人的，Focus 只提示「这个 canvasflow 等你处理」。

- 照子 agent 和委派会话折叠在父会话下的做法（`focus/FocusWorking.tsx` 的「▸ N」）：**一个 flow 一行**，它的会话不单独出现在顶层。状态取最要紧的那个：等你 > 停了 > 在跑。比如显示「画布流·xxx：2 处等你」。
- **点这一行打开画布，跳到等你的那张卡**，不是打开某个会话；展开这一行，能看到是哪几张卡在等。
- 提醒的键：`focus/attention.ts` 现在按会话算（`s:<会话>:<状态>`）。会话属于某个 flow 时，改成归到 flow 名下，比如 `f:<flow>:<等你的卡>`。新出现的等待照样会让小机器人提醒；同一个 flow 不会因为有 4 个会话就叫 4 遍。
- **命令批准**：未定。Codex 每条命令都要问，几个会话一起跑，问题会挤在一起；可以考虑每个 flow 设一个统一的批准方式（比如都用「帮我审批」），不然折叠成一行也省不了多少事。
