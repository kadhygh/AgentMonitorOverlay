# AMO 中转（Relay）· 让 AI 会话找人确认（2026-10-26）

> 状态：做完（第 1 阶段，2026-10-26～27：服务、客户端、命令行和 MCP，账号、热更新、服务器状态、话题、归档、布局改版）。第 2 阶段起被取代：团队任务、会话、文件和批注见 `plans/done/relay-tasks.md`，回复回到 Studio 会话见 `plans/done/relay-in-sessions.md`，2026-11-05 那一轮见 `plans/done/relay-round-2026-11-05.md`。进度流水 2026-11-06 删掉了，原文见 git 历史（提交 f46907f2 之前的版本）。几处后来变了，已在正文里标出：服务搬到了 Mac mini、登录改在平台、平台装的客户端不自己更新外壳、团队流程入口 10-28 收起来了。

## 为什么

策划和 AI 推进案子时，常有要程序确认的问题。现在的做法：策划提交一轮到 Git → 程序看提交、审批 → 再回给策划，很麻烦。
要一个中转工具：**AI 会话直接发一条「请求」给某个人，对方在自己的面板上看到、逐条回答，回复回到发起方。**

先作为独立程序做在 AMO 仓库里（同便签、Reviewer 的做法），跑通后再考虑并进 AMO Studio。

## 已定（用户 2026-10-26）

- 传输：**局域网中转服务**（HTTP + WebSocket），不走共享文件夹 / IM / Git。
- 范围：**同一局域网的小团队**（几到十几人）；不做公网。（最初定的身份是「名字 + 团队口令」，同天下午改成账号密码，见下；10-28 起登录只在平台，见 `AGENTS.md` 约束第 7 条。）
- AI 客户端：每个人用的都不一样（Studio、Claude Code、Codex……）→ **以 MCP 为主**，一个独立的 stdio MCP 服务，任何支持 MCP 的客户端都能接。
- 回复形式（第一阶段）：**逐条回答 + 自由文字 + 结论**（同意 / 需要改 / 有疑问）。行批注放第二阶段。
- （补充）**人和人之间也能直接发内容**（普通聊天）；**聊天记录存在服务器上**，换电脑、重装托盘程序都还在。

## 数据

- **对话（thread）**：两种。`direct`：两个人之间的私聊，每对人只有一个；`request`：每条 AI 请求单独开一个对话，标题就是请求标题，之后的回复和追问都在里面。（第 2 阶段起 `request` 升级成会话，见 `plans/done/relay-tasks.md`；10-27 又加了话题，见下。）
- **消息**：`text`（普通内容）/ `request`（正文 + 问题列表）/ `reply`（逐条回答 + 补充说明 + 结论）。每条都记作者，以及是本人发的还是 AI 代发的（带客户端名，比如 Claude Code）。
- 消息按服务器全局序号排；每人每个对话记一个已读位置，未读数从这里算。
- 名字不能重复。

## 组成

```
AI 客户端 ──stdio──▶ relay MCP ──HTTP──▶ 中转服务 ◀──HTTP/WS── 托盘程序（每人一个）
                    （读本机身份）        （存请求和回复）          收件箱 / 发出的 / 回复
```

1. **中转服务**（`packages/relay`，Node，`node:sqlite`）：成员、请求、回复、已读状态；WebSocket 推送「有新请求 / 有新回复」。最初设想由某个人的托盘程序在本机开服务，实际是无界面单独跑在团队服务器上（见下「中转服务跑在 Mac 上」）。
2. **托盘程序**（AMO 中转）：单实例、托盘图标、新消息时托盘气泡提醒。发出的请求收到回复后有「复制回复」（格式是给 AI 读的），网页版聊天的人也能用。设置保存在 `%APPDATA%\AMO Relay`。
3. **relay MCP**（同一个包里的 stdio 入口）：读本机托盘程序的设置拿到身份和地址。第一版的工具是 `relay_people`、`relay_ask`、`relay_replies`、`relay_wait`；`relay_ask` 的说明要讲清楚：请求发出就返回，不要干等，`relay_wait` 受客户端工具超时限制，只当辅助。（第 2 阶段改成 `relay_session_*` 等，10-27 去掉了旧名的别名，现在的工具见 `packages/relay/src/mcp.ts`。）

## 阶段

1. **最小闭环**：服务 + 托盘程序 + MCP；内容只有 Markdown 正文和问题。本机两个身份互发也能测（e2e 起一个服务、两个客户端）。
2. **接上 Reviewer**：请求里带**快照**，就是把文件内容、重点行、diff 打包进请求。程序那边打不开策划没提交的文件，所以查看包要能做成快照。程序在 Reviewer 视图里写行批注，批注作为回复的一部分发回去。（实际做法改了：文件和批注做在中转自己的查看器里，见 `plans/done/relay-tasks.md`「文件和批注」；「在 Reviewer 里打开」11-05 定为不做，见 `plans/done/relay-round-2026-11-05.md` 第 2 节。）
3. **回到会话**：Studio 管的会话收到回复后自动接回去；外部客户端照旧取回复，或者复制回复。（见 `plans/done/relay-in-sessions.md`。）
4. 以后：程序让自己的 AI 先起草回复、一个请求发给多个人、并进 AMO。

## 补充（用户 2026-10-26）

- **一键复制用法 prompt**：推进中随时粘给任何 agent，让它知道怎么用。文字只在 `usage.ts` 一处生成，托盘的「复制用法」、`amo-relay prompt` 和 MCP 的 instructions 都用它。
- **中转服务跑在 Mac 上**：服务只用 Node 自带的模块加 ws，打包成单个 `amo-relay.mjs`，要求 Node 22.13 或更新；Mac 上的部署和 launchd 写在 `packages/relay/README.md`。托盘程序跑在每个人自己的机器上，目前是 Windows。（现在服务在团队服务器 Mac mini `http://172.16.8.85:47120/`，部署走 `npm run release -- relay-service`，见 `AGENTS.md`；10-26 最初是部署在本机。）

## 补充（用户 2026-10-26 下午）：先出一个能直接跑的客户端，发链接给同事一起测

- **账号密码**：注册时填名字、密码，以及负责什么；服务带邀请口令时还要填口令。登录后每台设备拿一个 key。客户端会**记住账号和密码**：密码用系统加密保存（Windows 上是 DPAPI，Mac 上是钥匙串），登录页可以选已存的账号。（10-28 起登录只在平台：平台装的客户端只显示「在 AMO 平台里登录」，手动解压的客户端暂时还留着自己的登录框，见 `AGENTS.md` 约束第 7 条。）
- **热更新整个客户端**：界面放在服务器上，由 `relay-ui` 构建；桌面外壳固定不变。启动顺序：读条 → 连接服务器并检查版本 → 第一次打开时下载界面，有新版本时在读条里直接装好 → 进入登录页。
  运行中**自动更新**（10-26 用户问「能自动更新吗」后定的）：发布后服务通过 /ws 推送 `client` 事件，登录页从 `/api/health` 读到新版本。客户端只在不会丢东西的时候自己更新：登录页上要求还没动过表单；登录后要求窗口没在用（在托盘里、最小化了，或者没有焦点，由外壳的 `inUse()` 判断），并且没有草稿和打开的对话框。更新就是重新载入窗口，登录状态和当前打开的对话都会保留（sessionStorage）。条件不满足时，显示「有新版本 · 不用时自动更新」和「立即更新」按钮。外壳本身变了的话，提示重新下载。
- **更新桌面程序**（10-27 用户说「单独写个更新专用的界面，这样就不用单独下载再重新解压了」后加的）：外壳构建号和服务上的不一样时出现「桌面程序可更新」，点开是单独一页（`ShellUpdate.tsx`），「更新并重启」由外壳自己做（`updateShell`：下载、校验 sha256、解压、只换内容有变化的文件、出错全部还原、重启）。
  - 为什么这么做：靠一个比程序活得久的脚本来换文件不可靠（父进程退出时 Windows 可能把子进程一起结束，WMI 起进程在这台机器上也不执行）；整目录 3757 个文件逐个换会在中途被结束（原因没查清，同步、异步都一样），而两次构建之间通常只有程序自己的 JS 变了，exe 和 DLL 不变。新版连 Electron 本体（`resources\` 以外的文件）也变了时不在运行中换，提示手动换一次。没有 `updateShell` 的旧外壳只显示手动换的三步。
  - （10-28 起：平台装的中转不做这个「一键更新外壳」，外壳由平台安装和更新，因为它会改写程序文件夹里平台共用硬链接的 Electron 文件，见 `AGENTS.md` 约束第 3 条。）
- **服务器状态**（同一天加的）：登录页显示「服务器在线 · 地址」；连不上时显示「! 服务器离线」，带离线时长、每 5 秒自动重试、「立即重试」和「换一个地址」，登录按钮不可用。登录后，名字旁边显示「在线 / 连接中 / 离线」；断开超过 1.5 秒提示断开多久、几秒后重连，并有「立即重连」，这时成员的在线状态显示为未知。服务每 20 秒发一次 tick，客户端超过 45 秒没收到任何消息就判定断开，所以服务所在的电脑睡眠或断网也能发现。读条阶段连不上时也每 5 秒自动重试。
- 下载页 `/`：发给同事的链接。上面有 Windows 客户端的 zip，也可以直接在浏览器里用（`/app/`）。

## 补充（用户 2026-10-27 测试后提的三条）

- **话题**：每个人和对方之间有一个「普通聊天」，一直都在，不能归档，也没有删除。旁边可以开任意多个话题（带标题），每个话题单独记录，「复制对话」只复制当前这一个。对话顶部是标签栏：普通聊天、各个话题（按开启顺序排），最后是「＋ 新话题」。
- **归档**：只影响自己的列表。已归档的收进默认折叠的「已归档」分组；有新消息时，所有人那边都会自动放回列表。普通聊天不能归档。不做删除。
- **气泡**：自己的消息靠右，底色浅绿；对方的靠左，带头像和名字，底色浅灰。同一个人 5 分钟内连续发的纯文字不重复显示头像和名字。请求和回复卡片保留左侧的色条。
- 发布前 e2e 先跑在临时构建上（`AMO_RELAY_E2E_RELEASE`），通过后才发布到正在运行的服务；客户端页面里出现任何未捕获的错误都算失败。
