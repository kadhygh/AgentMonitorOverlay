# 全景（panorama）：方案和阶段（2026-11-01 起，讨论中）

来历见同目录 `README.md`（三层架构、datalayer 规范、deck.gl 原型）。这份只写全景接进 Studio 之后怎么往下走。

## 已定

- **名字**：「全景」，id `panorama`。用户特意选中性名：渲染主题（星图、冰白全息……）以后给别人用时可以换，数据结构稳定。
- **入口**：设置 → 测试功能（默认关，和默认开的「功能」/`disabledFeatures` 分开存 `experimentalFeatures`）；开了之后顶栏「画布」后面多一个「全景」。
- **视觉**：先只做冰白全息（`v-deck3.html#oblivion`），风格参数在 `ui/src/panorama/themes.ts` 一张表里。
- **由简到繁**：正式迭代从最少的内容开始，以后再加（用户 11-01）。
- **渲染由代码做、只读 datalayer**：`ui/src/panorama/datalayer.ts` 把 Studio 状态转成 0.2 的形状，页面只读它。super-agent 原型（DSH 团队，`deepseek-ai/dsh-superagent-prototype`）也是面板由代码从事实渲染、不交给模型。

- **几张全景**（用户 11-02）：以后允许建多张，但大多数情况一张就够，渲染哪些节点更该由**筛选器**决定。开发期间先只有一张。
- **节奏**（用户 11-02）：一项一项来，现在只专注**场景效果和最初的表达**（P1）；要点和审阅等问题先记着，推进到了再说。
- **和 AMO 的边界**（用户 11-02）：全景以后可能拆成偏独立的模块、只内嵌在 AMO 里，也可能实验不成整个砍掉，所以现在不专门整理，但守住两条：① 只有 `datalayer.ts` 读 AMO 的东西（专题、任务、会话的状态，`@amo-studio/protocol` 的类型，AMO 的其它模块）；`PanoramaPage`、`layout`、`engine`、`themes` 和以后加的绘制代码只认 datalayer 的形状，不 import protocol 或 AMO 的模块。② 全景要 AMO 做的事（打开任务、跳到会话……）都经页面传进来的回调（现在是 `onOpenTask`），绘制层不直接调 AMO。接 AMO 的只有 `view.tsx`（Studio 里：取状态、只读画布依赖、跳页面）和 `preview.tsx`（预览：读快照）；预览页和 Studio 共用绘制代码，正好检验这两条。

## 节点的表达：从起点长向终点的树（用户 11-01）

- **起点**：任务创建时立一个明显的起点标志。
- **主干**：一个会话算一轮，主干每轮长一节，节点标「第 N 轮」。
- **分叉**：分支会话、用 session_start 开出去的会话从开它的那一轮岔出去；并回收回主干，放弃的停住变暗。子 agent 不画。
- **终点**：创建时就在前方淡淡显示，表达「一直在向终点进发」。有清单时按没勾的项定距离；没有清单时终点总在最新进度前方一小段。
- **前进的动向**：最新节点到正在跑的那一轮之间有光点往前流；没在跑就停。
- **到终点**：看板列决定：「待审」列终点亮一半（等你验收），「完成」列路接上终点、点亮。
- **任务之间**：画布的依赖、引用用 3D 弧线（原型里的效果用户认可）。
- **远中近**：远只看起点、主干长度、等你的亮点；中看每轮节点和分叉；近再给牌子加一行内容。

**为什么试 A/B/D（用户 11-02，看了 P1 第一版）**：一条细线配一个大框，比例失调，树显得单薄；地图倾斜着看，贴在地上的线被压扁，远看几乎没有存在感；每一轮长得都一样，没有节奏，看不出哪轮干得多。所以：D 底座（贴着树的胶囊代替大框，名字和状态挂在底座边上）、A 轨道（路做成一条带子，走过的部分填亮，每轮一道刻度）、B 天际线（每轮一根光柱，高度按这轮干了多久，立起来就不怕被压扁，也有了高低节奏）、E 工程图细节（尺寸线、边缘刻度、坐标，点到为止）。

**用户 11-02 又提的四点**（都先只在预览页试，开关在风格表 `PanoramaLook` 里，Studio 还是 P1 的样子）：

1. **前锋**：最前面的那个节点始终是一根更高更亮的柱子，路上朝终点方向画 `›››`。任务在跑时箭头一个接一个往前流、光往柱顶灌；没在跑时箭头静止、暗一些，但「最前面在哪、朝哪走」一直看得出。
2. **压缩顺利推进的轮**：第一轮、最近两轮、开过分叉的、等你的轮保留；其余连续 ≥3 轮压成一段，像折起来的手风琴挤在一起，旁边标「×N 轮」，路上画坐标轴截断记号。拉近到中景或点那一段就展开（展开状态记在页面里，不进 datalayer）。哪些轮能压只看 `layout.ts` 的 `foldRuns` 一个函数，以后有「要点」数据再加条件。
3. **占地大致固定**：每个任务的路有长度上限，在里面「近疏远密」：最近几轮间距大，越早越往起点挤；和压缩一起，推进一百轮占地也基本不变。
4. **曲线但有共同流向**：路可以弯，但要有整体的流向，不要各弯各的。两版：`flow`（推荐）整个专题一个平滑的「风场」，所有路顺着它弯，相邻的大致平行、不交叉，底座跟着路弯；`spiral` 以专题中心为原点，各任务从中心附近起步，像旋臂一样同一旋向往外卷。支线跟着主干的局部方向走。

## 要点和审阅（先记着，推进到 P3 时再谈）

一轮回复是一大篇，里面夹着要人认可的点。设想：

- **来源**：以干活的会话每轮结束时用工具自己交要点为主（一句话一条，标「需要你拍板」或「告诉你一声」）；没交时由便宜模型补抽，先观察模式（只标记，不算数），人觉得准了再放开。借鉴 super-agent：只认结构化字段，不从自由文字推断在等人。
- **平时**：要点是挂在那一轮节点旁的卫星点，远看不显示，节点标「3 点」；只有「需要你拍板」的让节点变成等你。
- **两种审法**：一次看完点「全部认可」，要点收进节点；或逐条认可 / 批注 / 搁着，批注攒进「批注篮」，看完「发回」合成一条消息给那个会话（复用 Reviewer 的「批注N」引用）。
- **审完**：要点变成 datalayer 的正式条目（决定、结论、出处）；被批注还没解决的就是下一轮的起因。
- **待定**：来源这样分主次行不行；没审的要点挡不挡任务（建议不挡，只有「需要你拍板」算等你）。

## P0 留下的问题

- 「等你」只算会话在等人；`decision_request` 的决定没画进来，和顶栏「需要你」的数字可能不一致。
- 牌子只写状态和会话标题，看不出具体在等什么。
- 有等你的事时提示动画 30 帧一直刷新；deck.gl 任何报错或 15 秒画不出来就退成列表，可能偏保守。
- 没测：任务很多的专题、高 DPI；Esc 和其他窗口的冲突。

## 样子在试（11-02）

一条线太单薄，预览里在试底座、轨道、天际线、工程图细节四样（风格表的开关，地址后缀 `#base` `#a` `#ab` `#ad` `#abd` 切换，见 README「P1 补」）。Studio 里先保持 `#base`，用户挑定再切。

接着试上面的四点（README「P1 再补」）：后缀 `-flow` `-spiral` `-wave` 选路怎么弯，同时带上前锋、压缩、固定占地，`-nofront` `-nofold` `-nospan` 单独去掉一样；不带后缀的 `#abd` 等还是上一版的样子。预览页不写 `#` 时是 `#abd-flow`。长任务的演示数据：`?data=panorama-snapshot-long.json`（`node plans/userlayer/panorama-demo-long.mjs` 生成，40 轮和 100 轮两个虚构任务）。

## P1 留下的问题

- 用 session_start 干活的任务（比如 amo-flowmaptest：第 1 轮开了 8 个会话）主干很短、活都在支线上，远看「主干长度」不代表进度；现在远看也把支线淡淡画出来，终点按最前面的节点算。
- 一个会话开的会话合成一条支线，按开始时间排开；支线多了往上下两侧一条条排开，区域会变高（日常维护有 10 个，排得下）。分支再开分支没在真实数据里见过，只有单测。
- 有会话在跑时光点一直流（20 帧），CPU 不会降到 0；没在跑、没等你、没选中时停。
- 终点：没清单时总在最前节点前 24 个单位；有清单时每个没勾的步骤远 0.6 轮（最多算 15 步）。真实数据里没有清单，距离感只在演示数据里看过。
- 依赖弧从被等的任务的终点连到等它的任务的起点，弧会跨过中间的区域。
- 名字：有底座时挂在底座下面、加了牌子底，前排光柱和终点光晕不再穿过字；但后排名字仍可能落在前排的路上（被牌子底盖住），长任务演示里「百轮演示」的名字和它第一段「×19 轮」挨得很近。
- 压缩：一百轮里一段能压几十轮，压着时那一簇柱子在远处还是一团亮；拉到中景全部展开后，早期的轮挤得很密（固定占地的代价），要看清得再拉近。
- spiral：中心附近各臂的起点挤在一起，任务多了会更挤；依赖弧从外圈连回中心，横穿别的臂。
