# 带过来的小问题（阶段 8 之后）

ROADMAP 的阶段都完成后，剩下的都在等你。这里记录 loop 在等待期间看过的遗留小问题，以及结论。

| 问题 | 结论 | 处理 |
|---|---|---|
| e2e 里用 Codex 会话的用例偏慢（25 秒左右） | 查清了：不是 MCP 慢——Host 层面一次 Codex MCP 调用约 0.1 秒。慢在**测试结束关闭应用**：大约一半的运行里，Host 停止 Codex app-server 时等进程退出的 5 秒超时被用满，之后 Electron 进程退出又被拖住约 17 秒（Electron 已经发出 `quit`，Playwright 还在等进程真正结束）。另一半的运行里全程不到 1 秒 | **暂不修**：只影响测试耗时（完整 e2e 约 5–7 分钟），不影响使用——正常使用时 Host 常驻，关窗口不会停 app-server。要彻底修需要换掉 Windows 上结束进程树的方式，收益不大 |
| 交接终端里的 Claude 不带 AMO MCP | 要带上，就得把 MCP 地址和令牌写进 Claude 的 MCP 配置（命令行参数或配置文件），和"令牌不上命令行、尽量不落文件"的红线有冲突 | **先不做**：交接终端本来就是你亲自在用，需要 agent 读看板时可以收回到工作台再继续。如果你希望带上，告诉我，我按"令牌只放在数据目录的配置文件里"的方式做 |
| 测试偶尔留下临时目录 | 原因是删除时 Codex 进程还没退干净（文件被占用），删除已经带重试（最多约 10 秒）；和上面第一条是同一个根源 | **不改**：loop 每轮结束都会清理 `%TEMP%` 下的 `amo-studio-test-*`、`amo-studio-e2e-*` |
| 完整 verify 时 `server-manager` 的"崩溃后同一端口重启"偶发失败 | 单独跑总是通过；完整跑（测试文件并行、机器忙）时，被杀掉的 app-server 的端口有时超过 10 秒都没释放，重启只好换端口，后面两个用例跟着失败。等待时间试过加到 10 秒也不够，已改回 3 秒（再长会拖慢真实崩溃后的恢复） | **已修（2026-11-03）**：真正的原因是 app-server 后台 `git fetch` 插件市场时，那个 git 继承了监听端口，偶尔被 `taskkill /T` 漏掉（实测：杀掉后端口的 Owner 仍是已退出的 codex，它的子进程 git.exe 还在 fetch github.com/openai/plugins）。测试改用 `-c features.plugins=false` 启动，hook 超时放到 60 秒；连跑 8 次、全量都通过。同一次修复：值守单测里连跑几个 `node -e` 命令的用例在机器忙时会超过 vitest 默认的 5 秒，整组测试的超时改成 30 秒 |
| 自动打包的单测偶发失败（2026-11-02 15:26，AMO 平台 0.9.14，master 4195d1e9；11-01 的 Studio 0.9.24 第一次也是这样） | 值守在值守目录和打包目录里用同一条命令（`npx vitest run --maxWorkers=6 --retry=1 --exclude …server-manager.test.ts`，BelowNormal）各重跑一次，都全过（163 个文件、1071 条）。是哪条用例失败查不到：自动打包的输出没有留下来。另外问题页的进度条停在「类型检查」，其实类型检查已经过了，是「单测」这一步的进度没报上去（报进度失败只打日志、不重试） | **记录**：在问题页点「发布打包」重试，或者等 master 下次变动时自动打包自己再试。反复出现时再让 `release.mjs` 把失败用例的名字带进问题页的提示，好定位是哪条 |
