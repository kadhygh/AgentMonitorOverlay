## 为什么做（用户 2026-11-23，Obsidian 画布「架构讨论」）

现在的流程：策划推进 designdoc → 给程序出红绿灯 → 程序按红绿灯给开发建议 → 策划在自己分支上开发 → 程序复审 → 程序合回主干。卡在：

- designdoc 穷举不了落地时的边界情况，第一版很可能被推翻；
- 红绿灯时给的时间少，程序只能给大方向，减少不了多少返工；
- 复审时程序只能从红绿灯反推实现和架构，又不够了解 designdoc 的核心，于是策划、程序要审批大量边界条件，「信息密度过高」；
- 这套流程是为了策划不空转，代价是这时程序在空转。

用户的思路：边界情况一定有。测试中、没敲定的，AI 补上建议的边界情况、走默认；已确定的，边界情况都要写明。要减少审批量，就把需求打散，不让人一次审太多。

做法：用中转搭一个 Cowork。相关的人和他们各自的 agent 都在里面，各有身份；有共同的目标说明和补充；人和 agent、agent 和 agent 之间交流来补全内容（大多数时候是人和 agent）。需求定下后，策划发起 Cowork、定分支，把相关的人拉进来，每个人再把自己的 agent 会话拉进来。这样步长变小，程序的 agent 早点介入，不用攒一大堆、让人一口气审到上下文爆掉。

用户手上没有能当参考的真实记录：本地只有程序合并的记录，正好是步长太大、审核爆炸的例子。做完后用户找几个人一起试。

## 用户定的（2026-11-23）

- **agent 结构先精简**：每人带自己的 agent，不设专门的传话或审核 agent。
- **Cowork 是一个功能**，里面有一层共享数据，白板是它的一种表现方式；另外要有工作群聊天的感觉。
- **白板第一版就要有**，参照无限画布做，AI 和人都能往上放东西；Studio 的画布可以借来改。
- **Cowork 里也要有本任务的白板**，保证共享信息有人推进；但项目里的正式内容还是以 A、B 的 agent 写进分支的文档为主。
- **子会话**：A 的 agent 发给 B 一个要确认的关键问题，成为 Cowork 里的一个小的子会话。B 可能要多轮，所以在群里折叠成一张卡，所有人都能点开看、能插话。它就是现在的「中转会话」（以前是 AI 代问，人传话或直接回复给 AI），只是所有人都能看到、都能插话。
- **@ 和重要提问**：A @B 让 B 确认；B 确认时可以一键跳到自己的 Studio 会话，把它转过去。
- **B 插话不开 fork**（批注 1）：B 补充的很可能是关键信息，之后还要在 A 的会话里接着做，开 fork 又浪费缓存。所以就在 A 的会话里接，只管时机和显示（见「插话」）。
- **AI 不被别人的聊天唤醒**，只有 @ 它时才唤醒（批注 9）。
- **AI 发起 @、提问做成 Cowork 的一个选项，默认关**（批注 9；关着时怎么办见「还要确认的」第 1 条）。
- **没有 Studio 的人**只装了中转客户端，就只以人的身份在 Cowork 里说话（批注 8）。
- **测试**：可以用 dxx-ds、gpt6.2sol、sonnet 跑真模型场景；跑之前照 `budget.json` 计数。

## Cowork 里有什么

一个 Cowork 是中转服务器上的一份数据，不是一个模型，也不常驻 agent（守 `canvasflow-direction`：不要常驻看板员）。

| 部分 | 是什么 |
|---|---|
| 成员 | 人（团队账号），加上人拉进来的 agent。agent 显示成「A 的 AI · 会话名」，一个人可以拉多个会话进来 |
| 目标说明 | 发起人写的目标和补充，所有人可改，留历史；顶在 Cowork 最上面。还记下仓库和分支（发起时定） |
| 群聊 | 主流，像工作群：文字、@、文件（走现有附件，传文件做好后可以引那条通道） |
| 子会话 | 一件要确认的事：标题、谁问的、等谁、状态（开着 / 等某人 / 已定）、结论。群聊里折叠成一张卡，在原地更新；点开是它自己的多轮对话，成员都能插话。结论定下时记进「已定的事」 |
| 白板 | 无限画布：便签卡、子会话卡、引用卡（文件、提交、文档的某一版）、分组、连线、颜色。人在中转客户端里拖，AI 用 MCP 写 |
| 已定的事 / 事件 | 子会话的结论、目标的改动、谁推了哪个提交。只记不叫醒人，agent 要时自己读 |

## agent 怎么参加

- **拉进来**：人在自己的 Studio 会话里点「拉进 Cowork」（或在中转客户端的 Cowork 里选「拉我的会话进来」，跳回 Studio 选会话）。拉进来就算授权这个会话在这个 Cowork 里回复、写白板、记事件，不用每条再确认。
- **唤醒**：只有两种情况会叫醒它：有人 @ 它；有人回复了它发起的子会话。别人在群里聊天不叫醒它，它下次醒来时由 Host 带一句「Cowork 里有 N 条新的」，要看再用 MCP 读。
- **送进会话的时机**：Host 现在就用长轮询等中转的消息（`host/src/features/teamrelay/service.ts` 的 `loop`），再放进会话收件箱。Cowork 照这条路走：这一轮跑完才送；人正在打字或有没答的审批时也先不送（交流框架规则 5，`plans/collab-framework.md`）。
- **在对话里的样子**：一件子会话、一次 @ 折叠成一张卡（交流框架规则 6），不把人正在谈的主线顶走。
- **给 agent 的 MCP**（Host 的 teamrelay 加，名字暂定）：`cowork_read`（目标、新消息、开着的子会话、已定的事；可只读某个子会话）、`cowork_post`（群里说话或回复子会话）、`cowork_ask`（发起子会话，受下面的选项管）、`cowork_board`（读写白板）、`cowork_note`（记事件，比如「推了提交 abc123，改了 `设计/xxx.md`」）。

### 插话（A 在和自己的 agent 谈，B 插进来）

- B 在群里或子会话里 @A 的 agent：先挂在它名下排队，不打断这一轮；这一轮完了才作为一轮送进 A 的会话。同一个会话往后追加，缓存照常命中。
- A 的对话里，B 这一来一回折叠成「B 插话：…… / 已回复」一张卡。A 看到的还是自己的主线，agent 却已经知道 B 补充了什么。
- 不需要 A 那边上下文的问题，B 问自己的 agent 就行：它读 Cowork 和分支文档来答，A 的会话不动。

### 人输入时看到的 agent 状态（用户 11-23 要考虑）

人在输入框里打字、@ 某个 AI 时，要知道这句话发出去之后会怎样，不用猜。

- **AI 的状态**（由它主人的 Studio 报给服务，经 /ws 推给协作里的人）：
  | 状态 | 意思 | 这时 @ 它会怎样 |
  |---|---|---|
  | ✓ 待命 | 会话空着，主人的 Studio 开着 | 马上送进它的会话，开一轮 |
  | ◐ 处理中 | 正在跑一轮（可能在回别人） | 排队，这一轮跑完再送；显示「前面还有 N 条」 |
  | ! 等主人 | 主人正在和它说话（输入框里有字），或有没答的审批 / 草稿等主人确认 | 排队，主人这边空下来再送 |
  | ○ 不在线 | 主人的 Studio 没开或断线 | 留在服务上，主人的 Studio 连上后送；显示「上次在线 10:42」 |
- **在输入框里**：@ 补全列表里每个 AI 后面带它的状态；选中后，输入框上方一行写清楚「程序老李 的 AI 正在处理（前面 1 条），你这句会在它这一轮之后送到」。发出后，消息下面显示这条的去向：排队中 → 已送达 → 已回复。
- **AI 回的是谁**：AI 的回复带「回 美术小周」，在群里引用那条消息，不和别人的对话混在一起。
- **人正在打字时，AI 的新消息不抢输入框**：新消息照常进群，但不滚动、不打断，底部出「有 2 条新消息」。
- 第一版不做「AI 正在输入…」这种逐字状态，只做上面四种。

### B 一键转到自己的会话

B 在子会话卡上点「转到我的会话」：跳到 B 的 Studio，选一个会话或新开一个，把这个子会话的全文送进去。那个会话也就被拉进了这个 Cowork，可以替 B 回复（显示「B 的 AI」），或者 B 看完自己回。中转客户端已经有「在 Studio 里打开」，照它的路走。

**接法（第 4 步定，给第 3 步用）**：中转客户端只要把子会话的 threadId 交给本机 Studio 的 Host，Studio 自己弹窗问「由哪个会话接手 / 新开一个任务」、拉进协作、送全文、跳过去。按钮只在桌面客户端里、子会话的 `request.coworkId` 有值、我在这个协作里时显示。

- **用现有的外壳就能接，不用改 `relay-app`**：调外壳已有的 `shell.openInStudio(conv)`（`relay-app/src/studio-link.ts`），`conv` 写 `studio:<本机设备号>:cowork-to-<threadId>`。外壳照旧找本机的 Studio、带 host-token POST `/api/ui/open {sessionId: "cowork-to-<threadId>"}`；Studio 认出 `cowork-to-` 前缀就当「转到我的会话」。返回 `null` 是成了（Studio 已弹窗并到前面），返回字符串是为什么没成（「Studio 没开着」等，直接 toast）；第 4 步之前的 Studio 会让外壳说成「Studio 里没有这个会话了（可能已经删掉）」，界面可以把它换成「更新 Studio 后再试」。本机设备号：`shell.transfer.device()`（传文件那版外壳起有）。按钮显不显示可以先问 `shell.studioHas(同一个 conv)`（本机有 Studio 在跑才是 true）。没有 `transfer` 的旧外壳拿不到设备号：按钮不显示，或提示更新中转桌面程序。
- **以后外壳要改时的正式接口**：Host 的 `POST /api/cowork/handoff {threadId}`（同样要 host-token），效果一样。接手的那一步是 Studio 界面自己调的 `POST /api/cowork/handoff/accept`，中转客户端不用管。
- Studio 收到后：要求我在那个协作里，否则报错；一小时没处理的自动收起；同一个子会话重复交只留一份。

## 信息怎么保持是新的（两台设备之间）

| 层 | 放什么 | 怎么保持是新的 |
|---|---|---|
| 分支（git） | 项目里的正式内容：A、B 的 agent 写的文档、代码 | 照常提交、推送。agent 推了之后用 `cowork_note` 记一条带提交号的事件（服务器看不到仓库，所以由 agent 报）；别的 agent 下次醒来看到，需要时自己 fetch |
| Cowork（服务器） | 讨论、子会话、已定的事、白板、还没到提交那一步的草稿 | 服务器只有一份，改动经 /ws 推给在线的客户端；agent 醒来时读 |

白板上的引用卡记下它依据的提交或版本。同一个文件有了更新的提交事件，卡上标「已过时」。不在两台电脑之间直接同步文件：两边同时改会冲突，正式内容只走 git。

## 白板怎么借 Studio 的画布

- Studio 画布的几何部分是纯函数（`ui/src/canvas/geometry.ts`：移动、缩放、分组、连线、曲线），数据结构在 `protocol/src/canvas.ts`；中转界面已经用相对路径引 `ui/src` 里的组件（`relay-ui/src/shared.ts` 引了 `FloatBox`），可以照样引。
- `CanvasPage.tsx` 和 Host、任务、专题绑得紧，不直接搬；在中转界面里写一个轻一点的白板组件，用同一套几何和卡片样式，卡片类型换成 Cowork 的（便签、子会话、引用）。
- 存在中转服务器上。Studio 的画布是一个人用，整份带版本号保存；协作的白板几个人和几个 AI 同时在改，不能整份存，改成下面「多人同时改」的做法。

## 白板：多人同时改（用户 11-23 要考虑）

一句话：**按卡片、按字段改，服务器排先后；同一张卡的文字同时只让一个人写；谁都能撤回，删掉的能找回。** 第一版不上 CRDT（卡片上的字短，软锁就够；以后要多人同时写长文再换 Yjs 一类）。

- **改动是一条条操作，不是整份文档**：加卡、移动、改大小、改文字、改颜色、连线、删除、进出分组。客户端把操作发给服务，服务给每条一个序号、写进白板、经 /ws 推给所有在看的人；每张卡有自己的版本号。
- **位置、大小、颜色**：后到的为准（按服务的序号）。拖动时只在松手时发一条（拖的过程只在本机和「在场」里显示），所以两个人同时拖同一张卡，最后松手的那个位置留下，另一个人看到卡跳过去。
- **文字：软锁**。有人开始编辑一张卡的文字，服务记下「小周 在写」，别人看到卡上标着，文字框是只读的，但还能拖动它、连线。锁 30 秒没动静自动放开；断线也放开。
- **AI 改正在被人写的卡**：不覆盖。服务拒绝这次修改，告诉 AI「小周 正在写这张卡」，AI 可以等一会再改，或者在旁边另放一张卡、连线指过去。
- **删掉 vs 正在改**：删除只是标记删除，白板角上「最近删除」能找回（留到协作结束）；别人正在写的卡不能删，会提示。
- **在场**：白板标题栏显示「3 人在看」，别人选中的卡带他的名字色边，正在拖的显示虚影。AI 改过的卡闪一下，角上标「AI 刚改」。
- **断线再连**：客户端把没送出的操作排在本机，连上后按顺序补发，每条带它基于的卡片版本。卡片已经被别人改过：位置类照样补发（后到为准）；文字类不覆盖别人的，服务把你的那版存成这张卡的「另一版」，卡上标「! 有冲突，看另一版」，由人挑一版。
- **撤销**：每个人只撤销自己的操作（Ctrl+Z），撤销本身也是一条新操作，不会把别人的改动一起撤掉。
- **历史**：每条操作都留着（谁、什么时候、改了什么），白板里能看一张卡的改动记录；大的改动（新卡、删卡、标已过时）同时记进协作的事件。
- **AI 写白板**：用 MCP 按卡片发操作（`cowork_board`：加、改、移、连、标过时），带它读到的版本；不能整份覆盖，也不能一次改别人的一大片（一次最多 10 张卡，超了要人点头（用户 11-23 按建议定）。

## 接口要点（给做服务的会话；细节由它定，写进 `relay/src/cowork-protocol.ts`）

尽量复用中转已有的东西，不另起一套：

- **协作的群聊 = 一个新类别的会话**（`ThreadKind` 加 `cowork`），协作的 id 就是它的会话 id；消息、附件、已读、/ws 推送、`/api/wait` 都照现在的走。成员只记人（账号）。
- **agent 的身份 = 它的会话标记**：Studio 发消息时本来就带 `Via { kind: "ai", conv }`（`studio:<设备号>:<会话 id>`）。协作另有一张表记「谁把哪个会话拉进了哪个协作」：标记、主人、显示名（「策划小王 的 AI · 射速文档」）、状态、上次在线。@ AI 用它的标记（消息加 `agentMentions`）。
- **子会话 = 现有的 request 会话加一个 `coworkId`**：成员是协作的全部成员（后来拉进来的人也加进去），谁都能看、能插话；问的一方、等谁、多轮、答复和结论都照现在的 `RequestState`。定下结论时记进协作的「已定的事」。
- **送给 agent 的东西排队**：被 @ 或它发起的子会话有人回复时，服务给这个 agent 记一条待送（排队中 → 已送达 → 已回复），主人的 Studio 拿走时确认「已送达」，agent 回复时引用那条，变成「已回复」。发消息的人看到的去向就是这三步。
- **agent 状态由主人的 Studio 报**：待命 / 处理中（前面几条）/ 等主人；Studio 断开或一阵没报，服务就当它「不在线」。变了经 /ws 推给协作的人。
- **AI 的草稿**：「AI 发起 @ 和提问」关着时，agent 发出的带 @ 人的消息和新子会话先存成草稿，只有主人看得到；主人点「发出 / 改一下再发 / 不发」。
- **白板 = 一串操作**：参照待办的做法（`relay/src/todo.ts`、`/api/todo/ops`：按条操作、服务给序号、删除只做标记）；卡片带版本号、软锁、「另一版」；操作全留着当历史；`GET …/board?after=序号` 补拉，/ws 推新操作。
- **目标、仓库分支、选项、事件**：协作本身的一张表，目标改动留历史；事件（谁定了什么、推了哪个提交、白板大改动）只记不推醒任何 agent。
- **给 agent 的 MCP 由 Studio 的 Host 提供**（`cowork_read / post / ask / board / note`，在 `host/src/features/teamrelay/`），中转自己的 MCP（`relay/src/mcp.ts`）这一版不加。

### 第 1 步做成的样子（2026-11-23，服务端）

接口清单在 `packages/relay/README.md`「协作」，类型和规则在 `relay/src/cowork-protocol.ts`，客户端方法在 `RelayClient`（`relay/src/api.ts`），单测 `relay/src/cowork.test.ts`。上面几条都照做了，下面是做的时候按常理定的，和要第 3、4 步留意的：

- **agent 的状态**：Studio 只报 `idle / busy / owner / offline`；「前面还有 N 条」由服务自己数（这个 agent 排队中的待送，`CoworkAgent.queued`），不用 Studio 报。Studio 至少 30 秒报一次，90 秒没报算「不在线」。
- **Studio 取待送**：`GET /api/cowork-inbox?prefix=studio:<设备号>:&wait=毫秒`（没有就等到有），送进会话后 `POST /api/cowork-inbox/ack` 记「已送达」。agent 在同一个会话（群聊或子会话）里再发言，就把它在那里「已送达」的待送都记成「已回复」；没写 `replyTo` 时，服务替它引用最近送达的那条。在那里定下结论、标记完成这类动作（不发消息）也算回过话（11-23 补）：agent 做的，记它自己的；人亲手做的，记这个人自己的 agent 的，别人的 agent 不动。协作结束时，还在排队的待送记成「丢弃」（结束了就没法在那里回话）。没 @ 它的群聊不进待送，只在 inbox 的 `unread` 里数条数（「Cowork 里有 N 条新的」）；agent 用 `GET …/feed?agent=<标记>` 读过就从那里重新数。
- **草稿**：「AI 发起 @ 和提问」关着时，AI @ 人、@ 别的 AI、新开子会话都算，先存草稿；不带 @ 的发言、在子会话里接着说，直接发。主人发出的消息带 `approvedBy`（改过再发的还带 `edited`），作者仍是 AI。AI 自己（`via.kind = "ai"`）不能决定草稿。
- **AI 之间连续往来的上限**（用户 11-23 补的护栏，和 `plans/collab-framework.md` 的轮数上限是一个意思）：同一个会话里（群聊和每个子会话分开数），AI 的消息连续到 `AGENT_STREAK_MAX`（30 条）、中间没有人说过话，之后 AI 的消息不再给任何 agent 记待送，同时记一条 `paused` 事件「AI 之间已经连续往来 30 条，等人看一下」推给协作里的人（只记一次）。有人在那里说一句话就重新数；拉人这类事件消息不算说话。
- **子会话的结论**：`POST …/sessions/:tid/conclude` 定（发起的人、被问的人或他们的 AI），或者在子会话上「标记完成」时写的说明。都记成 `decision` 事件，子会话上带 `conclusion`。
- **结束的协作**：不能再发消息、改白板、拉 agent，直到有人重新打开。删掉的卡一直留着（没有到期清理）。
- **白板**：文字的软锁走 HTTP（`…/board/lock`，写的时候每隔几秒续一次）；在场走 /ws 帧或 HTTP。AI 不占锁；AI 碰到有人在写的卡、或者在它读过之后改过字的卡，被拒绝（`locked` / `stale`）；人的同类改动存成「另一版」。AI 一次调用超过 10 张卡，整次拒绝（403）。commit 事件带的文件会把引用旧提交的卡标成已过时（记在那个 agent 名下）。
- **第 4 步（Studio）要留意**：AI 发起的子会话也是一个 request，`request.from` 是主人、`conv` 是它的标记，所以 Host 现在的 `teamrelay` 扫描（`dueForAi`）也会把回复当「中转回复」送回会话。接协作时要跳过 `request.coworkId` 有值的会话，只走待送，否则会送两次。
- **第 3 步（界面）要留意**：`/api/threads` 里有协作的群聊（kind `cowork`）和子会话（request 带 `coworkId`，协作里的人都在里面，不只是问和答的两个人）；待处理、聊天的列表要把它们滤掉，放到协作里显示。

### 第 4 步做成的样子（2026-11-23，Studio）

代码在 `host/src/features/teamrelay/cowork.ts`（拉进、状态、送进会话、转到我的会话）、`cowork-text.ts`（送进会话的文字、工具的回答）、`cowork-mcp.ts`（`cowork_*`）、`host/src/core/cowork.ts`（人下一条消息带的话）；界面 `ui/src/teamrelay/Cowork.tsx`。导航索引 `studio.cowork`。按常理定的：

- **入口**：会话「更多」菜单里的「拉进协作…」，弹窗选协作、填名字（只填「会话名」那段，前面固定是「我 的 AI · 」）。远程任务的副本、归档的会话、子 agent 没有这个入口。会话标题栏下一行写它在哪个协作、状态、排队几条、几条草稿等你，带「在中转里打开」（打开协作的群聊）和「退出」。
- **状态**：在跑 = 处理中；审批、提问、计划待审、在终端里、有协作草稿、有 team_ask 待发、人点了停止还没再写、输入框有字 = 等主人；其他 = 待命；会话没了或归档 = 不在线，并且自动退出协作（排队给它的作废）。每 30 秒全报一次，变了 0.3 秒后再报。输入框有字由界面在变化时和之后每分钟报一次（`POST /api/sessions/:id/composer`，只对在协作里的会话），Host 3 分钟没再听到就当空了。
- **送进会话**：只在「待命」时送；同一个会话同一个协作一次来的几条合成一条消息（一张卡）。消息开头一行 `【协作「标题」· 谁 在哪里做了什么】`，然后每条消息（带 #序号）、最后一段告诉它用 `cowork_post`（带 threadId、replyTo）回到协作里。先放进会话收件箱再 ack；ack 没成功的下次只补 ack，不再送一次。
- **「协作里有 N 条新的」**：服务的 `unread` 变多了，就在人下一条消息末尾带一句（和白板、脉络的提示同一个地方）；送进一批 @ 时也顺带说；agent 用 `cowork_read` 读过就清掉。为此服务的 `unread` 改成不算已经作为待送给它的那几条（`relay/src/cowork.ts` inbox，向后兼容）。被拉进协作这件事也在下一条消息（或第一批待送）里告诉它一次。
- **cowork_read**：不带 threadId 是全貌（目标、仓库分支、选项、成员和 AI 状态 + mark、开着的子会话、已定的事、最近的事件、它自己的草稿）+ 上次读之后的新消息，最多列最近 40 条；读到哪 Host 记着（kv），也可以带 after。带 threadId 是一个子会话全文加文件。
- **cowork_board**：Host 记着这个 agent 上次读到的每张卡的文字版本，改字时没写 base 就替它补上，所以「读过之后被人改过」会被服务拒（stale）。超过 10 张卡在 Host 这边就拒，告诉它分批、先在协作里说一声。被拒的每条都写明怎么办。
- **转到我的会话**：接法见上面「B 一键转到自己的会话」。Studio 弹窗列最近 30 个会话（主会话和分支，没归档、不是远程副本），或新开一个任务（项目 + 模型，任务名「协作：子会话标题」，会话名是子会话标题）。送进去的话让 AI 先和人在对话里商量，人让回时再用 `cowork_post` 回在子会话里。
- **不送两次**：teamrelay 的扫描跳过带 `request.coworkId` 的会话；AI 用 `cowork_ask` 开的子会话也只走协作的待送。
- 没做的：Studio 里不能决定草稿（在中转里发出 / 改 / 不发）；`cowork_*` 没有「定下结论」（`concludeCowork`），要的话再加一个工具；协作里的附件 AI 用 `team_file_get` 取（`cowork_read` 列出的子会话文件），群聊里的文件没列。
