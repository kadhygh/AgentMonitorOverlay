# 问题页 + 值守：报问题 → AI 修 → 定期发测试版

> 状态：做完（阶段 1–3 2026-10-31 做完，问题页当天部署；11-03 加了维护者和审核）。之后改了的已在正文标出：修复改在值守目录里做（10-31 晚），测试包由值守项「自动打包」发、不开模型（11-01，见 `plans/release.md`「维护节奏」），大的问题用「需要确认」在问题里谈（10-31 晚）。进度流水 2026-11-06 删掉了，原文见 git 历史（提交 f46907f2 之前的版本）。

2026-10-31 和用户定的方向。用途：迭代期用户凭自己的体感报 AMO 的小问题（附截图），AI 修，定期打包发测试通道，用户更新后再试。先只有用户自己报。

## 已定

1. **入口只在团队服务器的网页上**（中转服务那台，和下载页同一个服务）。各工具不加「反馈问题」按钮。问题的往来（提交、截图、AI 的追问和回复、状态、「发布打包」）都在这个页面上。
2. **报问题的只有用户自己**，目标是快速把 AMO 的基础操作流程磨顺，不做多人工作流。（11-03 起别人也能报，要维护者先审，见「问题页（服务器）」最后一条。）
3. **Host 加定时功能**，名字不和 Claude 的 loop、GPT 的 goal 重复（见下文「名字」）。
4. **打包时机**（最初定的）：修好待发的凑满 3 个；每 30 分钟检查一次，有修好的就发；用户在问题页点「发布打包」。（11-01 改了：值守项「自动打包」跑 `release.mjs auto --if-due`，一个工具最后一次改动后 30 分钟没有新改动、或最早的改动等了 2 小时、或人点了「发布打包」就发，见 `plans/release.md`「维护节奏」第 9 条。）
5. **只在有事时才开模型**：轮询、计数、到点都由代码做，不花 token。

## 流程（最初的设想）

阶段 3 改了做法（见下文），自动打包后来也不开模型了；这张图留着说明最初的思路。

```
问题页（服务器）──新问题──▶ Studio Host 的值守（每 N 秒问一次服务器，纯代码）
                                 │
                                 ├─ 建 AMO 任务「问题 #12 …」，开修复会话（Opus）
                                 │     ├─ 看不懂 / 复现不了 → 在问题页追问，等用户答（答复回到这个会话）
                                 │     ├─ 修好：单测/e2e 过，改动说明写进「下一版」，在修复车道提交
                                 │     └─ 卡住：问题页写卡在哪，状态「卡住」，Focus 提醒
                                 │
                                 └─ 打包条件满足（3 个 / 30 分钟 / 用户点了） → 打包脚本
                                       ├─ 升版本号、package:platform、publish 测试通道
                                       ├─ 问题页对应条目写「已修复于 x.y.z 测试版」
                                       └─ 脚本失败 → 才开一个会话去处理
```

## 模型

- **修复：Opus**，一个问题一个会话：理解、追问、修改、测试都在这个会话里做。只有一个人报、量不大，没必要用 Haiku 先分诊一次。
- 不设中间档。Opus 额度紧张时，值守自动改用备用模型（实际做法：用到 95% 换值守项设的备用模型，没有备用就跳过这次），并在问题页注明用的是哪个模型。
- 打包是脚本，不用模型；脚本失败才开会话。
- 以后报的人多了，再考虑加一个分诊步骤（查重、看信息够不够）。

## 名字

**值守**（代码里用 `duty`，2026-10-31 用户定）：Host 里一组「到点或有事 → 做一件事」的规则。界面上叫「值守」，规则叫「值守项」。

值守项的样子：

| 字段 | 例子 |
|---|---|
| 触发 | 每 N 秒（至少 10 秒）/ 每天 HH:MM，从上次开始（或改动）算 |
| 条件（可选） | 「先检查」：一条检查命令或 Studio 自带的检查，见「阶段 3 改了做法」 |
| 动作 | 在某个任务里用某个模型开会话（带固定提示），或每次新建任务 / 跑一条命令（低优先级、去掉 Host 自己的变量、默认 30 分钟超时）/ Studio 自带的项（功能自己登记，只能开关和改时间，不能删） |
| 并发 | 同一个值守项同时只跑一个；上一个还在跑就跳过这次 |

规则：
- 开会话之前先查额度；Studio 退出后值守就停，下次启动接着跑（重启时把没等到结束的那次标成失败）。
- 会话停下来——推进过、出错、被打断、已有完整回复、或开了 15 秒都没动——这次才算完。
- 值守不重启 Host，也不替用户点更新：平台更新 Studio 会打断正在修的会话，所以更新由用户在空闲时点。

## 修复车道

**2026-10-31 晚改**：不再每个问题开 `issue/<编号>` worktree，改在值守目录（master 的 detached worktree）里修、`release land` 合进 master；测试包 11-01 起由值守项「自动打包」发。见 `plans/release.md`「维护节奏」和模板 `docs/prompt-templates/issues-duty.md`。下面是之前的做法。

2026-10-31 用户定：现在只有用户自己在快速维护，一直没遇到过不该合进主线的改动，所以每个问题都走 **worktree → 修复 → 验证 → 合回 master**。

- 每个问题一个 worktree，从最新的 master 开，分支 `issue/<编号>`。在里面修复、跑验证（单测和相关的 e2e，低优先级），提交。
- 验证通过就合回 master（先 rebase 到最新的 master，能快进就快进）。合完删掉这个 worktree 和分支。有冲突或验证不过就停下，问题标「卡住」，在问题页和 Focus 里说明原因。
- 修复一个接一个做，不并行，免得同时改到同一处。
- 打包从 master 打。
- 这条车道里的**自动提交和合并**是 AGENTS.md「用户要求才提交、不自己合并」的例外，已写进 AGENTS.md。只限值守处理问题页上的问题。

## 问题页（服务器）

- 地址 `/issues`，和 `/admin` 一样是局域网里的普通页面，用团队账号登录（key 存在浏览器里）。问题存在中转自己的数据库里（`relay/src/issues.ts`），改登录名时跟着改。
- 提交：一句话或一段描述，加截图（粘贴或拖入，可以多张）；可选工具（Studio / 便签 / Reviewer / 平台 / 中转）和版本。打开页面时，平台可以把本机已装的各工具版本带进链接（`#key=…&v=studio:0.9.16`），这样就不用手填。
- 每个问题一个对话流：用户的描述 → AI 的追问和回复 → 用户的补充。状态（`relay/src/issues-protocol.ts` 的 `ISSUE_STATUS_LABEL`）：待审核、打回、新、修复中、需要确认、已修好待发布、已发布、卡住了、去会话讨论、不修了。用户在已修好、已发布、卡住、不修了的问题下面再写话，问题会重新打开。
- 「需要确认」（10-31 晚，用户：「不用再有建议单开讨论，issue 本身就能多轮交流」）：AI 看不懂、或问题大，写清打算怎么做，在问题里一轮一轮谈。「去会话讨论」只由人点（「前往讨论」），值守不碰。
- 顶部：待发 N 个、上次发布的时间和版本、「发布打包」按钮；正在打的测试包和它停在哪一步也显示在页面上。
- 服务器只存问题和对话；Studio 通过 API 拉取和回写，用平台存的账号（`account.json`）访问。
- 维护者（2026-11-03 用户定）：账号上的身份，在管理页设，默认谁都不是。维护者看得到所有问题，自己提的直接是「新」；非维护者只看得到自己的（列表、单个问题、截图都挡），提的先是「待审核」。维护者「确认制作」后变「新」，记下 `approvedBy`，以后重新打开不用再审；「打回」要写原因，提交人再回一句就回到「待审核」。没确认过就关掉的，再打开还是「待审核」。只有维护者能改状态、代 AI 回复、发布打包、标已发布、前往讨论；AI（值守）不碰「待审核」「打回」的问题，服务端也拦着。规则在 `relay/src/issues.ts`。

## 阶段 3 改了做法（2026-10-31 用户定）

值守只在用户自己维护 AMO 时才开，所以不做内置的值守任务、不做打包脚本，改成**一个普通的提示词模板**：用户需要时自己建一个值守项（开会话），话里点名模板，AI 照模板做。

- **会话用的工具**（Host `features/issues/`，AMO MCP，都不用批准）：`issue_list`（默认只列没结束的；`release.requestedAt` 是「发布打包」的请求）、`issue_get`（全文；截图下载到数据目录 `issue-images/`，给本机路径）、`issue_reply`（写一条，可带本机截图、可同时改状态）、`issue_update`（状态、worker、标题、fixedIn）、`issue_released`（发完测试版，把这些问题标成已发布、清掉打包请求）。都用平台登录的账号，写的内容标成 AI 的；没登录时提示去平台登录。
- **模板原文**：`studio/docs/prompt-templates/issues-duty.md`（标题「问题页值守」，项目 AgentMonitorOverlay）。现在的内容：先看有没有事，没事一句话结束；一轮最多 3 个问题，先判断大小（看不懂或大的写清打算怎么做、标「需要确认」），小的在值守目录里修、验证、提交、`release land`，不行就标「卡住」；测试包不用它打，「上一次打测试包没成功」时去查；不重启 Studio、不 promote、不部署中转服务。值守项由模板「开始维护」设（`docs/prompt-templates/start-maintenance.md`）。改了这个文件要同步到 Studio 里的模板。
- **值守项的会话设置**：值守项可以给开的会话指定型号、思考强度和权限（没人看着时要选不用逐条询问的权限）；额度不够改用备用模型时用它自己的默认设置。
- **先检查，有事才开模型**（用户批注，2026-10-31：「每次都先走脚本，有问题才拉起ai」）：会话类值守项可以设「先检查」——跑一条检查命令（有输出、退出码 0 = 有事；没输出 = 没事；别的退出码 = 检查失败），或 Studio 自带的检查。问题页的自带检查「问题页有事要做」（`issues.pending`，代码写的）：有新问题、人在问题下回复了（「去会话讨论」的除外），或上一次打测试包没成功（11-01 起；原来这里还算「该打包了」）。检查发现的内容接在提示词后面（「值守检查发现：」）。和上次开会话时一模一样的发现不再开（检查结果里不带时间，同一个状态读出来一样），检查说没事时清掉这个记录。
- **建议的值守项**：开会话、模型 Claude 选 Opus、权限选不用询问的那档、在固定任务「问题页值守」里开（不要每次新建任务）、**每 30 秒**、先检查选「问题页有事要做」；话写「照提示词模板「问题页值守」做」。检查只是一次 HTTP 请求，不花额度。
- 修不了时 AI 把问题标成「卡住」：同样的发现不会再开会话，不改状态就没人接手。

## 值守给 AI 用（2026-10-31 用户定）

场景：「写个脚本检查 xxx，每 30 分钟跑一次，有问题就拉起 AI 审，没问题了就停」，整件事对 AI 说一句就行。

- **不做通用的 if/else**：判断写在脚本里。值守只给脚本三种结局——没事（没输出）、有事（有输出，开会话，输出接在提示词后面）、结束（输出一行 `AMO_DUTY_DONE`，这次之后关掉值守项；还有别的输出时先开会话处理这最后一次）。命令类值守项也认这一行。
- **AI 的工具**：`duty_list`（只读）、`duty_save`（新建或修改，**每次要人批准**：值守开了就会自己跑命令、开会话、花额度；默认用调用者的模型、在它自己的任务里开会话、命令在它的项目文件夹里跑；列表标「AI 建的」，人自己改过就去掉这个标记）、`duty_stop`（关掉，不用批准；值守开的会话不带 id 就是关开它的那一项）。
- **untilDone**：会话类值守项可以勾「AI 判断事情做完……可以自己关掉」，开会话时提示词末尾告诉 AI 做完调 `duty_stop`。没勾的（比如一直要跑的问题页值守）不加这句，免得 AI 把它关了。
- amo_guide 的 files 一节写了这几个工具和脚本的约定。
